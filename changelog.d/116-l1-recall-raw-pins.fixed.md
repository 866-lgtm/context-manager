- The canonical L1 compression prompt shows a message a pin keeps raw as raw, as the live view does, where the pins fit its budgets (next item); it used to recall the summary covering it. A frontier summary that covers such a message is descended rather than recalled: its children take its place, so only the branch holding the pin opens, sibling branches stay recall pairs, and the raw a pin adds is its own L1 chunk. An opened chunk renders raw wherever it lies before the chunk being compressed, including before the head window. The head window always comes first; after it, recall pairs and raw messages go in source order, so the summarizer doesn't read old turns as coming after later memories. Empty-content frontier summaries above L1 are descended the same way, and an empty L1 that holds no pin stays covered, as before. Only opened chunks lose coverage: a merged L1 that its parent doesn't list stays covered, as before, unless a pin opens it. Only pins before the chunk being compressed count, so a summary after it is recalled as before. Merge recall, L3+ merge inputs, transition summaries and the source-only L1 do not consult pins.
- An L1 prompt shows pinned history raw only when it fits. The raw that pins add is spent from `compressionRecallBudgetTokens` first, and recall pairs get the rest, oldest dropped first as before. The request with it must also fit `compressionContextBudgetTokens`, priced as the message store prices the messages it would send, with the system prompt, tools and output reserve. When either fails, that compression lays history out as it would without pins: it recalls the summaries the pins override, and pinned history before the head window that no summary covers is left out, as before. A warning and a `compression:pinned-raw-over-budget` log event name the pins, the sizes and the limit. Waiting instead would stall every later L1, since the pinned history precedes each of them. The live view still shows the pins raw, and a canonical request without pins is still always attempted.
- A pin resolves once, for compression, chunking and every selector (the strategy's `resolvedPinBounds`). Level bounds are read only under `foldingStrategy: 'kv-stable'` and `'kv-unified'` with `adaptiveResolution`, with kv-stable's precedence: where pins overlap at a message, a bound takes a classic pin's place, `level` takes `maxLevel`'s, and the lowest of each kind wins; a level or cap of 0 is raw. Under every other selector a pinned message is raw, as `pinAtLevel` documents, so the flat-profile and oldest-first folders no longer fold a message pinned with a level. Picker chunks carry one reading: a raw pin, a level or cap of 0 included, is `pinned`, so kv-unified no longer asks for an L1 of a chunk pinned at level 0, and `pinLevel` and `pinMaxLevel` are set only above 0. kv-unified's constraint source for such a chunk is now `raw-pin` (it was `classic-pin`). Under kv-unified, a `level` and a `maxLevel` that overlap no longer conflict: the `level` applies, as under kv-stable. Under kv-stable and kv-unified, a message pinned at a level or cap above 0 before it was compressed is now compressed, since only a summary can supply its level; before, the chunker skipped every pinned message, so no summary ever covered it. A message pinned that way before this change, whose neighbours have since been compressed and merged, gets an L1 of its own that nothing merges, so kv-stable renders it at L1, and kv-unified still can't reach a higher level for it.
